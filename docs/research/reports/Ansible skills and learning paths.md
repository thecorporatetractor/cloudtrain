# Build CloudTrain's Ansible domain on VMs, not containers

CloudTrain's Ansible domain should be built as a **four-rung ladder that mirrors Red Hat's exam structure**: playbook and role authoring (EX294), then advanced development and content packaging (EX374), then platform operations (EX467), with network automation (EX457) and Event-Driven Ansible as side branches. What runs underneath matters more than how the curriculum is laid out. The skills that make up the RHCE-style core (services, firewalld, SELinux, LVM, reboot persistence) **do not work in unprivileged sshd pods**. They need KubeVirt VMs, or Kata microVMs once those are validated. Cheap containers are good only for the fundamentals tier. The tooling baseline also moved in 2025. **ansible-core 2.19 made templating stricter and requires conditionals to return booleans**. Exam objectives now include developer workflow: ansible-navigator, VS Code, Git, and dev containers. Lab content written against older tutorials will break, and labs that leave out navigator and Git will miss what the exam now tests. On licensing, a purely hosted service has light GPLv3 obligations. Shipping images to self-hosted customers is a different matter: it brings source-offer duties for every GPL component. AWX (Apache-2.0) is the only controller CloudTrain can legally host without a Red Hat agreement, and its releases have been paused since July 2024. Red Hat's trademark rules forbid using exam codes such as EX294 in course identifiers. The certification mapping therefore has to stay an internal design artifact.

## Four exams form a three-tier ladder plus a network branch

Red Hat's objective pages describe a clear progression, but the naming and versions are in flux. **EX294's official page now names the credential "Red Hat Certified Advanced System Administrator in Ansible"**. Passing it counts toward "Red Hat Certified Engineer in Ansible" and "Red Hat Certified Architect in Ansible". The same page is internally inconsistent, and the research found no announcement that explains the rename ([Red Hat EX294](https://www.redhat.com/en/services/training/ex294-red-hat-certified-engineer-rhce-exam-red-hat-enterprise-linux)). Third-party sellers list a RHEL 10-based EX294. Some of those listings carry stale "Ansible Engine" boilerplate ([UMBC Training](https://www.umbctraining.com/courses/red-hat-certified-engineer-rhce-exam-for-red-hat-enterprise-linux-10-ex294/)). The RHEL 9 URL and the generic URL return the same objective list ([Red Hat EX294 RHEL 9](https://www.redhat.com/en/services/training/ex294-red-hat-certified-engineer-rhce-exam-red-hat-enterprise-linux-9)). Red Hat says objectives follow the most recent product version, and several exam versions are live at once. CloudTrain should therefore map to **objective themes, not exact wording**.

The table paraphrases each exam's scope and separates what is current from what is legacy.

Three patterns run across all four exams. First, **the automation content of EX294 barely changed**: modules, templates, Vault and roles. The changes were in the developer workflow (VS Code, Git push, dev container, navigator config). CloudTrain's lab image therefore needs code-server, an in-cluster Git server such as Gitea, and navigator on the control node, not only ansible-core. Second, every exam is a **4-hour performance test graded on freshly installed systems with no internet**, and that constraint maps directly onto CloudTrain's offline design ([UMBC Training](https://www.umbctraining.com/courses/red-hat-certified-engineer-rhce-exam-for-red-hat-enterprise-linux-10-ex294/)). Third, **no Event-Driven Ansible exam exists** in the sources. There is a DO274 introductory course, and one reseller's "exam included" claim is unverified ([New Horizons DO274LS](https://www.newhorizons.com/course-outline/courseid/300201565/coursename/introduction-to-event-driven-ansible-red-hat-learning-subscription-course-do274ls)). EDA should be a skills track with no certification framing. The older EX407 and EX447 exams appear retired, but this was not verified.

## ansible-core 2.19 reset what "correct" playbooks look like

The 2025-2026 baseline is **ansible-core 2.19 through 2.21**. Version 2.19 shipped on 21 July 2025 and reaches end of life in November 2026. Version 2.20 shipped in November 2025. Version 2.21 shipped in May 2026 and runs on Python 3.12-3.14. The current community package is **Ansible 14, which bundles core 2.21** ([Ansible release and maintenance](https://docs.ansible.com/ansible/latest/reference_appendices/release_and_maintenance.html)). This matters because of 2.19's breaking changes, listed in the porting guide ([Porting guide 2.19](https://docs.ansible.com/ansible/latest/porting_guides/porting_guide_core_2.19.html)). Templates inside untrusted strings, such as module output, are no longer rendered. Only native Jinja types are supported, and multi-pass templating such as `1 + {{ x }}` is gone. **`when:` conditionals must return real booleans**, so truthy strings and nested `{{ }}` now fail. Become timeouts now report the host as unreachable rather than failed, and variables carry data tags that record their origin, which improves error messages. The 2.19 roadmap also moves password SSH from sshpass to SSH_ASKPASS and starts deprecating paramiko ([Roadmap 2.19](https://docs.ansible.com/ansible/latest/roadmap/ROADMAP_2_19.html)). For CloudTrain this is both a risk and a teaching opportunity. Every lab and every grader playbook must pass on 2.19+. "Migrate a broken pre-2.19 playbook" is also a realistic advanced exercise that competitors' older content does not cover.

Platform tooling moved too. **AAP 2.5 introduced a unified platform gateway.** AAP 2.6 added unified RBAC, EDA support for external secret managers (HashiCorp Vault, CyberArk, Azure, AWS), Kafka multi-topic sources, Lightspeed, a self-service portal, and standardized `AAP_` environment variables ([AAP 2.6 release notes](https://docs.redhat.com/en/documentation/red_hat_ansible_automation_platform/2.6/html-single/release_notes/index)). AAP 2.7 documentation also exists ([AAP 2.7 docs](https://docs.redhat.com/en/documentation/red_hat_ansible_automation_platform/2.7/platform_intro)). Red Hat's own interactive labs cover ansible-builder, collection signing, Windows, ServiceNow and EDA rulebooks. That confirms these topics as mainstream rather than niche ([Red Hat interactive labs](https://www.redhat.com/en/interactive-labs/ansible)).

## Eight learning paths hang off the RHCSA spine

The paths below are design proposals derived from the taxonomy. The hour figures are estimates, not sourced benchmarks. The structure follows the exam ladder, and **the main dependency is the Linux domain**. EX294 explicitly includes the RHCSA baseline. Its largest objective group is "automate RHCSA tasks with modules". The credential is awarded only to holders of RHCSA ([Red Hat EX294](https://www.redhat.com/en/services/training/ex294-red-hat-certified-engineer-rhce-exam-red-hat-enterprise-linux)). EX457 likewise recommends RHCSA-level Linux plus routing and switching knowledge ([Red Hat EX457](https://redhat.com/en/services/training/ex457-red-hat-certified-specialist-in-ansible-network-automation-exam)).

| Path | Prerequisites | Content | Capstone / outcome |
|---|---|---|---|
| **A. Ansible fundamentals** (~8-12 h) | Linux domain: CLI, SSH, sudo, editors | D0, D1, early D2 (conditionals, loops, handlers, templates) | Idempotent playbooks for a small fleet |
| **B. RHCE-aligned automation** (~25-35 h) | Path A; Linux domain's RHCSA path | All of D2; a module drill for every RHCSA category; navigator, VS Code, Git | Timed mock exam on fresh VMs, graded after a reboot |
| **G. Engineering practices** (~10 h) | Path B | ansible-lint, Molecule, ansible-test, CI, EE pipeline, 2.19 migration | Lint-clean, Molecule-tested role in a pipeline |
| **C. Advanced developer (EX374-aligned)** (~25 h) | Path B (G recommended) | D3 plus D4 testing | Collection with a role and a custom filter, packaged in an EE, published to private Galaxy, run from AWX against a dynamic inventory |
| **D. Platform operator (EX467-aligned)** (~20-25 h) | Path C, or B plus controller basics | D5 | Multi-team RBAC org, survey templates, approval workflow, API-launched jobs, instance group, backup/restore |
| **E. Network automation (EX457-aligned)** (~15-20 h) | Path A, B's D2 core, networking domain basics | D6 network, controller workflows, config-as-code | Render configs from Jinja2 and back up configs on virtual routers |
| **F. Event-driven and self-healing** (~8-10 h) | Path D (or A for CLI-only rulebooks), K8s monitoring basics | D6 EDA | Alertmanager alert, then a rulebook, then a job template that remediates |
| **H. Windows automation** (~6-8 h) | Path A | D6 Windows | Deferred until Windows licensing is resolved (see licensing below) |

The bridge to the Linux domain should be explicit and reciprocal, not just a prerequisite link. Every RHCSA task in the Linux domain can have an Ansible mirror lab that uses the same golden VM image and **the same end-state checker**. One check, such as "httpd enabled on port 82 with the correct SELinux port label, persisting after a reboot", validates both the manual Linux lab and its automated Ansible counterpart. That halves grader authoring. It also teaches the idea the exam rewards: a playbook is a repeatable statement of the same system state an administrator would otherwise configure by hand. Learners who arrive with RHCSA skills fast-track through Path A. Learners who come in through Ansible need the Linux path's storage, SELinux and systemd units first, because the modules are meaningless without the underlying concepts.

Lab format should copy the three market patterns. Red Hat runs 15-60 minute single-topic browser labs on preconfigured AAP environments ([Red Hat interactive labs](https://www.redhat.com/en/interactive-labs/ansible)). KodeKloud pairs a control-node terminal with a quiz panel, starting with multiple-choice questions and moving to harder hands-on tasks ([KodeKloud lab intro](https://notes.kodekloud.com/docs/Ansible-Advanced-Course/Core-Components/Lab-Introduction-Demo/page.md)). LabEx publishes a "skill tree" of short labs with difficulty ratings ([DEV/LabEx](https://dev.to/labex/hands-on-ansible-setup-conditionals-loops-stat-module-labs-209c)). CloudTrain should offer three formats: micro-labs of 15-45 minutes, module labs that run quiz then tasks, and multi-hour exam simulations with hidden grading on fresh nodes. Exam simulations must avoid presenting themselves as official preparation, for the trademark reasons below.

## Runtime tiers follow module needs: sshd pods, Kata, then KubeVirt

The deciding constraint is that **systemd in an unprivileged container remains fragile on cgroup v2**. systemd needs a fully writable unified hierarchy. The published Molecule and Docker recipes rely on `privileged: true` with `cgroupns_mode: host`, and even then Rocky Linux containers are reported to fail with D-Bus errors ([jeffgeerling.com](https://jeffgeerling.com/node/3250); [trfore/docker-debian12-systemd](https://github.com/trfore/docker-debian12-systemd)). Podman's automatic systemd mode does not exist for Kubernetes pods ([iximiuz labs](https://labs.iximiuz.com/tutorials/systemd-containers-podman-30992811)). Unprivileged systemd pods have been shown on CRI-O with user-namespace annotations ([neteye-blog](https://neteye-blog.com/?p=43211)), but not verified under containerd. The comparable products use full VMs: NDG's NETLAB+ pod for RH294 is built from VMs ([NDG RH294](https://netlab-docs.netdevgroup.com/content/redhat/rh294_rhel9/podinstall/)), and KodeKloud's newer course assumes RHEL 10 control and managed nodes ([KodeKloud prerequisites](https://notes.kodekloud.com/docs/AI-Assisted-Ansible/Prerequisites/Prerequisites/page)).

The module-support matrix below is engineering inference and was not verified against sources. It shows why tiering is unavoidable.

| Capability | Tier A: unprivileged sshd pod | Tier A+: Kata pod (systemd image) | Tier B: KubeVirt VM |
|---|---|---|---|
| Files, templates, lineinfile, users, packages (via mirror) | Yes | Yes | Yes |
| service/systemd, crond actually running | No | Yes | Yes |
| firewalld | No | Yes (own kernel) | Yes |
| SELinux modules | No (host kernel) | Depends on guest kernel and policy; unvalidated | Yes |
| LVM, mount, extra disks | No | Possible with virtio disks; unproven | Yes (DataVolume/emptyDisk) |
| Reboot persistence | No | Pod restarts, may lose state | Yes; disk and IP survive |

Each module type should map to the cheapest tier that can run it. **Tier A** runs 3-5 sshd containers per learner (Rocky, Alma, UBI or Debian, with a sudo-enabled `student` user). It serves the inventory, ad-hoc, templates, variables, loops, roles and Vault labs, which is most of Path A. **Tier A+** is Kata pods with a systemd image. These are the safe way to run systemd containers, because privileged runc pods are unacceptable in a multi-tenant cluster and the Kata guest kernel becomes the isolation boundary. Use Tier A+ for service and handler labs once validated. **Tier B** is KubeVirt VMs from a golden Rocky or Alma qcow2 with cloud-init and attached disks. Path B's RHCSA automation, every exam simulation, and anything involving SELinux, LVM, firewalld or reboot must run on Tier B. That fits the platform's existing `vm` driver and golden-snapshot approach.

**The control node** should be a jumphost image with pinned ansible-core, ansible-lint, code-server, git and pre-distributed SSH keys. It should also carry ansible-navigator set to `--execution-environment false` in `ansible-navigator.yml`, so navigator uses host-installed collections and needs no nested Podman ([PyPI ansible-navigator](https://pypi.org/project/ansible-navigator); [AlmaLinux forums](https://forums.almalinux.org/t/installed-ansible-collections-not-showing-up-in-ansible-navigator/6772)). Labs that teach real execution environments or ansible-builder are the exception. They need a KubeVirt control node running Podman and pointed at a local registry that mirrors the EE base images. Podman inside an unprivileged pod needs `/dev/fuse` and user namespaces, or privileged mode, so it is off the table there.

**Offline content** uses documented primitives. `ansible-galaxy collection download -r requirements.yml -p <dir>` fetches collections and their dependencies at build time and writes an installable `requirements.yml` for offline hosts ([docs.ansible.com: Downloading collections](https://docs.ansible.com/ansible/latest/collections_guide/collections_downloading.html)). Galaxy NG, a Pulp plugin with a `pulp/pulp-galaxy-ng` image, can serve as an in-cluster private Galaxy. It supports remote sync and `ansible-galaxy collection publish` ([galaxy-ng docs](https://docs.ansible.com/projects/galaxy-ng/); [Docker Hub](https://hub.docker.com/r/pulp/pulp-galaxy-ng)). The recommended pattern is to bake collections into the jumphost for speed and point `ansible.cfg` at Galaxy NG only in the collection-teaching labs and in Path C's publish capstone. One Pulp deployment running pulp_rpm, pulp_deb and pulp_ansible could also host a curated Rocky/Alma/Debian package subset and container images, so a single service would act as the cluster's offline content hub. This is an inference; pulp sync configuration was not verified. Python dependencies that collections need on the node, such as netaddr, jmespath and pywinrm, go in as pre-built wheels.

**Network targets** should start with FRR, which is GPL and fully redistributable, and Nokia SR Linux, pulled publicly from `ghcr.io/nokia/srlinux` ([npa-showcases](https://github.com/commitconfirmed/npa-showcases)). Both run through containerlab, which is BSD-3, or Clabernetes. **Arista cEOS requires a registered account to download** ([containerlab cEOS](https://containerlab.dev/manual/kinds/ceos/)). Sources conflict on whether a free account is enough or a maintenance contract is needed ([PyPI eos-downloader](https://pypi.org/project/eos-downloader)). cEOS should therefore be bring-your-own-image per tenant. EX457 assumes Cisco, Juniper and Arista CLI familiarity, so FRR and SR Linux cover the `netcommon` and resource-module skills but not vendor-specific muscle memory.

**AWX sizing** shapes Path D's economics. AWX releases have been paused since 2 July 2024 for a refactor into a service-oriented architecture, with installation-method changes announced. The license remains Apache-2.0 ([github.com/ansible/awx](https://github.com/ansible/awx); [jeffgeerling.com](https://www.jeffgeerling.com/blog/2024/saying-lot-while-saying-nothing-all-about-ansible-awx)). Unofficial sizing guidance puts a minimum instance at about 1.75 CPU, 6 GB and 20 GB of storage, and a comfortable basic deployment at about **4 CPU and 8 GB** ([mintlify AWX requirements, unofficial](https://www.mintlify.com/ansible/awx/installation/requirements)). Per-container requests are tunable through operator CR fields ([awx-operator README](https://github.com/ansible/awx-operator/blob/2.5.3/README.md)). At that footprint, per-learner AWX costs more than a whole Tier B lab. There are three options: a shared AWX per cohort with per-learner organizations and RBAC (cheapest, weaker isolation); a pre-warmed pool of per-learner instances restored from a PostgreSQL snapshot; or deferring controller labs. A shared instance suits Path C's controller touchpoints. Path D's RBAC and backup tasks need isolated instances. Several EX467 objectives, namely hub upload, mesh and AAP backup, behave differently in AWX and would need adapted tasks.

### Grading verifies end state, then idempotency, then reboot

Graders should **inspect system state, never playbook text**, because that matches how Red Hat grades: playbooks applied to fresh systems, with configuration required to survive a reboot ([Red Hat EX374](https://www.redhat.com/en/services/training/red-hat-certified-specialist-developing-automation-ansible-automation-platform-exam)). The rest of this section is engineering recommendation; the notes cite no sources for grader mechanics.

The Go grader should run in four stages. **State checks** come first: commands over SSH, the KubeVirt guest agent or `kubectl exec` (`systemctl is-active`, `getent`, `firewall-cmd --list-services`, `getsebool`, `lvs`, `findmnt`, `crontab -l`), or an internal verify playbook built on `assert`. **Idempotency** comes second: re-run the learner's playbook with the JSON stdout callback and require zero `changed` and zero failures. Third, for Tier B exam-style tasks, **reboot** the VM and run the state checks again. Last come **optional quality gates**: `--syntax-check`, drift detection with `--check --diff` against a deliberately mutated node, and ansible-lint at a chosen profile, mapped to skill tags. Mutation testing (break state, confirm the checks fail, restore) validates the checkers themselves. The grader must resolve each node's driver from the topology, because reboot, SELinux and LVM checks are meaningless on Tier A. All checker playbooks must target 2.19+ semantics. The callback field names and lint profile names need verifying against current docs.

## Licensing hinges on hosting versus shipping images

Start with the **facts**. ansible-core and most community collections are GPLv3-or-later. community.general also contains BSD-2, MIT and PSF files, marked per file ([community.general README](https://git.lsit.ucsb.edu/ansible-collections/community.general)), and ansible.posix is GPL-3.0-or-later ([Red Hat catalog](https://catalog.redhat.com/en/software/collection/ansible/posix)). AWX is Apache-2.0, and its logos and branding fall under Red Hat's trademark guidelines ([github.com/ansible/awx](https://github.com/ansible/awx)). Certified collections are distributed through Automation Hub, and **customers need an Ansible subscription to access and download them** ([Red Hat KB 4916901](https://access.redhat.com/articles/4916901)). A distributed container image carries the license obligations of every file in every layer, including files deleted in later layers ([VMware OSPO](https://blogs.vmware.com/opensource/2019/04/18/tracking-container-image-licenses/)). Tools such as Tern can generate notices and corresponding-source pointers ([LWN](https://lwn.net/Articles/785680/)). Many images ignore the letter of the GPL, and enforcement has so far been absent ([LKML 2026-03](https://lkml.iu.edu/hypermail/linux/kernel/2603.2/08795.html)). That describes a risk; it does not grant permission.

The **interpretation**, which is not legal advice and is not backed by an FSF source in these notes, follows from GPLv3 triggering obligations on "conveying". GPLv3 has no AGPL-style network clause. Running ansible-core in CloudTrain's own cluster, with learners reaching it through a terminal, is therefore arguably not conveying, and pure SaaS carries minimal GPL duty. **Self-hosted enterprise installs, offline bundles and customer-pullable registries are distribution.** Each image then needs license texts, notices, and either the source alongside or a written offer covering ansible-core, collections, FRR, BusyBox, coreutils, systemd and the rest. Concretely, CloudTrain should generate a syft SBOM per image tag, archive the matching upstream source tarballs or SRPMs for each release, and avoid unpublished modifications to GPL code. The BUSL-licensed platform stays clean if it invokes ansible-core as a separate process (CLI or ansible-runner) rather than importing its Python modules. CloudTrain-authored playbooks are not derivative works and can carry CC BY-NC.

**AWX versus AAP** is a straightforward split. AWX can be hosted and redistributed commercially as long as LICENSE and NOTICE are kept and AWX and Ansible logos are removed from the UI. AAP needs Red Hat subscriptions, and a multi-tenant hosted training product would likely need a partner-type agreement. CloudTrain should therefore use **no AAP images, no Automation Hub, and no certified collections**, substituting Galaxy community equivalents such as ansible.posix, community.general and arista.eos from Galaxy. Base images should be Rocky, Alma, Debian or UBI. Full RHEL images are not redistributable, and the UBI EULA terms were not verified. **Windows evaluation media forbids selling and live use** ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/389493/how-long-can-i-used-windows-server-evaluation-vers)). Path H needs SPLA-style hosting licensing or should wait until after year one.

**Trademark rules** carry the most product-visible constraints. Red Hat's training guidelines require word marks to be used only referentially, never as the leading or most prominent element of a course title, with the company name more prominent than the mark. They prohibit **Red Hat logos and Red Hat course or exam identifiers such as EX-numbers**, require a specific no-affiliation disclaimer, and reserve Red Hat certification training for certified training partners ([Red Hat Trademark Guidelines](https://www.redhat.com/en/about/trademark-guidelines-and-policies)). The project trademark policy bars the marks from product, service, company and domain names. It allows descriptive use only after a preposition ("plug-in for AWX", not "AWX plug-in") ([ansible/logos TRADEMARKS.md](https://github.com/ansible/logos/blob/main/TRADEMARKS.md)). In practice, a title such as "CloudTrain Automation Track: Configuration Management with Ansible" is acceptable in principle, while "Ansible Academy" or an ansible-labs domain is not. The EX294/EX374/EX467/EX457 mapping in this report must stay internal. Learner-facing paths should say only that skills are aligned to industry automation roles, without implying official exam preparation.

## Conclusion

The research changes the build order. The obvious plan is to start with cheap containerized playbook labs and add exam depth later. The evidence instead puts the **KubeVirt Tier B node, the shared end-state checker, and the reboot-and-rerun grader on the critical path**. These are what make RHCE-style content credible, and they can be shared with the Linux domain's RHCSA labs, so one investment serves two domains. The other strategic finding is that the market is in transition: templating under 2.19, navigator and dev-container workflows in the exams, a paused AWX, and fluid credential names. Content written now against ansible-core 2.21 and modern tooling will outlast older competitor catalogues, provided CloudTrain pins versions, keeps the exam mapping internal, and treats the controller tier as an optional add-on rather than a foundation.
